## What to build

CLI 和手动 HTTP 等共享 runtime 入口在初始化、恢复前取得全部持久数据的独占权；争用者明确失败，既有 runtime 继续工作。后续桌面入口自然遵循同一规则。

**接口与设计原因：** 在 open_runtime() 资源边界封装 Portalocker 3.2.0；Windows 显式使用 Win32Locker 与 pywin32，不修改全局锁后端。平台路径身份和锁实现保留可替换边界。

## Acceptance criteria

- [x] 聊天库与 SQLite checkpoint 的实际资源分别非阻塞独占；相同文件去重，内存 checkpoint 不取得持久锁；固定顺序取锁。
- [x] 全部锁取得前不初始化数据库、不执行恢复；任一锁失败释放本次已取得的锁，报告数据正在使用，不影响现有 runtime。
- [x] 锁覆盖整个 runtime 生命周期，数据库连接关闭后才释放；同一 runtime 内多个 Thread 正常并行使用，不按消息重新加锁。
- [x] 稳定旁路锁文件解锁后不删除；文件存在或 PID 不是占用权威。残留无锁文件可重新使用，异常退出后必须重新取锁成功才能继续。
- [x] 仅支持本机普通路径；统一相对路径及资源身份，检查父目录与路径别名，明确拒绝硬链接、符号链接、目录联接和网络共享，不能只按绝对路径字符串去重。
- [x] 锁句柄不继承给工具子进程；一个 runtime 结束后不因存活的工具子进程继续占锁。
- [x] Windows 多进程验收覆盖同库、仅部分库重叠、不同库、取锁失败回滚、异常退出和连接关闭后的锁释放；记录实际测试与尚未验证的场景。

## Implementation — 2026-09-29

- `open_runtime()` 在最外层取得数据所有权，再打开 ChatStore、checkpoint、装配 Agent 和执行恢复；通过 `AsyncExitStack` 先清理执行和关闭连接，再释放数据锁。CLI 与 HTTP 继续共用这个边界。
- `runtime/data_ownership.py` 封装 Portalocker 3.2.0，Windows 显式实例化 `Win32Locker`，不修改 Portalocker 全局后端。非阻塞争用抛出 `RuntimeDataInUse`，消息带具体数据路径；其他 I/O 错误保留原原因。
- 每个实际数据库使用稳定的 `<数据库路径>.runtime.lock` 旁路文件，文件关闭后保留；明确设置描述符不可继承。按统一路径顺序取锁，通过真实文件身份去重，全部成功后才初始化数据库。`.runtime.lock` 后缀保留给锁文件，不能配置成数据库名。
- `runtime/data_paths.py` 独立封装路径身份：校验原始路径全部父目录后解析最终路径，既检查实际文件身份，也检查不存在文件的父目录身份。拒绝硬链接、符号链接、目录联接等重解析点、UNC/设备路径、映射网络驱动器和歧义 Windows 文件名。
- 数据库使用归一后的配置副本，调用者传入的配置不修改。内存 checkpoint 不锁定其未使用的路径；同一 runtime 的 Thread 共用所有权，不额外加进程锁。
- 路径检查针对应用管理的本机普通目录；运行期间不得由外部程序重命名、替换或删除数据及锁文件，不承诺防御恶意并发修改文件系统。
