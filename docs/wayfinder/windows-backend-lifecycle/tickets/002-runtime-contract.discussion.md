## 单实例与托盘驻留（已确认）

2026-09-26，用户明确要求本地只运行同一份应用，关窗后常驻后台，提供托盘图标和右键退出入口。这修改了原先的关窗即退出行为，并将托盘驻留纳入本轮范围。

- 重复启动唤起已有应用窗口，共用既有后端，不因再次打开应用创建第二份后端。
- 关闭窗口：窗口隐藏，桌面宿主、后端和正在执行的 Agent 任务继续运行，托盘图标保留。
- 退出应用：通过托盘右键菜单明确发起应用退出，进入后端清理和进程回收流程。
- 既有正常退出约束继续适用于显式退出：结束应用及后端，给予有限清理时间，超时强制回收；不要求等待 Agent 任务自然完成。
- 宿主异常退出仍按既有约定回收所属后端和子进程。

这里将“关闭窗口”与“退出应用”作为两个不同操作使用，后续状态转换和验收均按此区分。

## 后端就绪标准（已确认）

2026-09-28，用户接受以下就绪标准：

- `open_runtime()` 已完成初始化和历史运行状态恢复。
- 后端已监听本次选定的端口，`GET /health/ready` 成功响应。
- Tauri 为每次后端启动生成新的启动标识，健康响应包含该标识；Tauri 校验匹配后才将页面状态切换为可用，避免误认其他服务或旧后端。
- 就绪检查不额外调用模型生成内容；实际模型请求失败在运行时报告。
- 原因：只有完成初始化且确认可连接的本次后端才接收页面操作，同时避免每次启动额外消耗模型 token 和等待生成。
- 启动标识传递见“桌面启动参数”，响应字段和探测节奏见“就绪检查响应与探测节奏”；整体启动期限见下节。启动标识只用于识别本次启动，不自动等同于访问认证。

## 启动等待期限（已确认）

2026-09-28，用户接受默认 60 秒、可配置的启动等待期限。

- 从 Tauri 接受本次启动开始计时，包含端口选择、runtime 初始化和就绪检查；切换候选端口不重新开始计时。
- 由 Rust 壳负责计时和超时处理，避免依赖可能卡在初始化中的 Python。
- 超时仍未就绪时，显示启动超时并回收本次后端；确认回收完成后才允许手动重试。
- 后端进程提前退出时立即报告错误，不等到启动期限结束。
- 60 秒是启动等待上限，不包括随后回收进程所需的时间；回收期限和配置字段见后文已确认章节。

## 正常退出清理期限（已确认）

2026-09-28，用户接受默认 10 秒、可配置的正常退出清理期限。

- 托盘菜单发起退出后，后端停止接收新任务，结束当前本地执行并释放资源。
- 清理完成就立即退出，不等待期限耗尽，也不等待 Agent 任务自然完成。
- 清理期限由 Rust 壳监督，超过期限仍未退出则强制回收本次后端及所属子进程，Windows Job Object 作为回收方向。
- 正常清理接入现有 `runtime.lifecycle.shutdown()` 及资源上下文退出流程；退出请求通道见下节，关闭顺序见“桌面后端退出清理顺序”。
- 10 秒是允许正常清理的期限；强制回收后的确认与异常处理见“强制回收确认期限与失败处理”。

## 正常退出控制通道（已确认）

2026-09-28，用户接受通过父子进程管道发送退出命令。

- Rust 将管道连接到托管 Python 的标准输入，并通过该管道发送退出命令。
- Python 的托管启动入口接收命令，协调 runtime 与 Uvicorn 关闭。
- 发送退出请求不依赖 HTTP 服务已经就绪；Python 尚未响应或卡住时，Rust 仍负责按期限强制回收。
- 原因：控制通道跟随本次子进程建立，可在 HTTP 监听前发送请求，且不要求通过控制台交互操作后端。
- 标准流分工及消息格式见“进程间通信协议”；EOF 行为见“控制管道失联”。监听任务的建立时机、初始化中退出和 SSE 关闭顺序仍需明确。管道可写入不代表 Python 已完成清理。

技术来源：[Windows 子进程标准输入输出重定向](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output)。

## 重试与退出并发规则（已确认）

2026-09-28，用户接受由 Rust 后端管理器统一串行处理以下规则：

- 连续点击重试只接受第一次，不创建重复后端。
- 旧后端及所属进程仍在回收时，不允许启动下一次重试。
- 启动或重试期间收到显式退出请求，停止启动流程并回收本次后端。
- 已进入退出流程后收到迟到的就绪响应，忽略该响应并继续退出；旧启动标识对应的响应不能改变新一次启动的状态。
- 页面通过 Tauri command 请求重试，Rust 根据当前状态决定是否接受；命令名见“页面与 Rust 的状态接口”，返回字段见“手动重试命令响应”。
- 关闭窗口仍只隐藏到托盘，不进入退出流程。

### 建议的模块划分（设计草案）

- React 使用统一的 Tauri command / event 和 HTTP / SSE 契约，不感知 Job Object、系统句柄或平台进程标识。
- 公共 `BackendManager` 负责状态转换、启动标识、就绪验证、超时、重试和退出协调，各平台共用。
- 公共控制协议定义通过标准输入发送的退出命令；管道句柄的创建和连接由平台实现处理。协议语义不因系统变化而改变。
- 在进程托管模块设置可替换接口，Rust 可用 trait 表达。Windows adapter 在内部管理 Job Object 和句柄；未来 macOS adapter 实现相同托管能力。
- 启动参数使用统一描述：Python 可执行文件、参数、工作目录及环境变量。`.venv\Scripts\python.exe` 是 Windows 开发态解析结果，不写入公共接口约束；macOS 使用其平台对应的解析方式。

建议公共进程接口只暴露少量完整操作，名称待定：

| 操作 | 调用方可依赖的约定 |
| --- | --- |
| 启动托管后端 | 建立进程归属和控制管道，返回可操作的托管实例；部分失败由模块负责回收，不将系统句柄交给上层拼装 |
| 观察退出 | 报告后端退出结果；主进程退出与所属进程全部回收必须可区分 |
| 强制回收并确认结果 | 回收本次所属进程，明确返回已完成、失败或超时；未确认完成时不能允许重试 |

父宿主异常退出后回收所属进程也是接口的行为约定，不能只靠公共管理器在正常退出时调用清理方法。macOS 未来实现必须独立验证这一能力，不能仅因方法名相同就认定满足约定。

## 端口绑定归属（已确认）

2026-09-28，用户接受由 Python 执行实际端口选择与绑定。

- Python 从配置起始端口开始尝试实际绑定，遇到端口占用则递增候选端口。
- 成功后保留该 socket 并交给 Uvicorn 使用，不通过关闭再重新绑定来交接。
- Python 把最终端口报告给 Rust；Rust 监督本次启动，并将验证就绪后的地址提供给页面。
- 收到端口报告只表示地址已确定，仍须完成已确认的就绪检查才能向页面开放操作。
- 原因：以实际绑定消除空闲检测与后续绑定之间的竞争窗口，同时避免 Rust 与 Python 之间跨平台 socket 交接的复杂度。
- 端口报告使用下节确认的逐行 JSON 协议；独占绑定与错误分类见“Windows 端口绑定与错误分类”，搜索边界见“后端配置”。

## 运行数据独占（已确认）

2026-09-28，用户接受同一份运行数据只允许一个 runtime 使用的规则。

- 在共享 `open_runtime()` 入口取得运行数据的独占锁，持有至 runtime 清理完成。
- 桌面托管后端、手动 HTTP 入口和 CLI 入口均遵守这条规则。
- 未取得锁的第二个启动者直接报告数据正在使用，不执行启动恢复，也不影响已运行的后端。
- 原因：当前恢复逻辑只识别本进程持有的执行，不能让新 runtime 将另一进程仍在执行的 Run 判为执行丢失。
- 跨平台锁的具体实现、数据路径身份、多存储路径的锁定范围、进程异常退出后的释放语义需要技术验证。

## 控制管道失联（已确认）

2026-09-28，用户接受仅在桌面托管模式下，将控制管道关闭（stdin EOF）视为托管关系终止。

- Python 检测到 stdin EOF 后主动进入清理和退出流程，即使此前未收到完整退出命令。
- 若 Python 卡住，仍依赖平台进程回收机制兜底；EOF 本身不构成进程已退出的证明。
- 独立 CLI 和手动 HTTP 启动不适用此规则；托管模式必须由启动入口明确区分。

## 桌面后端启动器的资源归属（已确认）

2026-09-28，用户接受增加桌面后端启动器，统一协调托管模式下 Python 内部的启动与退出。

- Tauri 负责进程托管、启动与退出期限、异常回收；Python 启动器负责内部资源生命周期。
- 启动器在耗时初始化前建立 stdin 控制监听，负责进入 `open_runtime()`、保留已绑定 socket，并通过 `Uvicorn Server.serve(sockets=[socket])` 启动 HTTP 服务。
- 托管模式下由启动器持有 runtime 上下文并向 HTTP 应用提供 runtime，避免 HTTP lifespan 再创建第二份 runtime。
- 退出时启动器协调初始化取消、`runtime.lifecycle.shutdown()`、HTTP/SSE 收尾与资源上下文退出；不能仅依赖 HTTP lifespan 收到 shutdown 后才开始 runtime 清理。
- Python 启动器与控制协议由 Windows 和未来 macOS 共用，平台进程托管差异仍封装在 Rust adapter 内。
- 清理顺序见下节；初始化中断的具体任务组织留待实现，不表示代码已实现。

本地依据：`open_runtime()` 已负责资源上下文退出和 runtime shutdown；`ApplicationLifecycle.shutdown()` 已提供重复调用共用同一清理任务的行为。见 [runtime 装配](../../../../packages/harness/shikigen/runtime/composition.py)和[应用生命周期](../../../../packages/harness/shikigen/runtime/lifecycle.py)。

## 桌面后端退出清理顺序（已确认）

2026-09-28，用户接受以下退出顺序：

1. 停止接收新任务，并通知 Uvicorn 停止服务。
2. 立即启动 `runtime.lifecycle.shutdown()`，结束 Agent 执行，使 SSE 可以收尾；不能等待 HTTP/SSE 请求全部结束后才启动 runtime 清理。
3. 等 HTTP 请求与执行清理完成，再退出 `open_runtime()`，关闭持久存储，最后释放运行数据独占锁。
4. 初始化期间收到退出，由桌面启动器取消初始化并清理已打开的资源；未创建 runtime 时，不依赖 runtime 已存在才能退出。

上述步骤共用已确认的正常退出期限（默认 10 秒），不为每个步骤重新计时。Rust 监督期限，超时则进入所属进程树的强制回收；确认期限及失败处理见下节。

## 强制回收确认期限与失败处理（已确认）

2026-09-28，用户接受强制回收后固定最多等待 5 秒确认完成，与正常清理期限分开计算。

- 强制回收确认针对本次所属进程全部退出，不能只凭 Python 主进程退出认定完成。
- Windows adapter 使用 `TerminateJobObject` 发起强制终止，通过 `QueryInformationJobObject` 查询所属活动进程数；公共接口返回回收结果，隐藏 Windows API，供未来 macOS 实现相同语义。
- 5 秒耗尽仍未确认，或查询失败时，报告“无法确认后端已完全退出”，禁止重试启动。该期限是等待确认的预算，不是操作系统保证全部进程在 5 秒内退出。
- 保留托管实例及回收观察能力，继续观察；不能因报告错误就丢弃确认所需的资源。
- 显式退出时出现该错误，显示并保留错误窗口；后续确认回收完成后自动完成应用退出。
- 未发起应用退出的启动失败或后端故障，后续确认回收完成后才可按既有规则开放手动重试，不自动启动后端。

技术依据见[底层机制调查](../../../research/windows-backend-lifecycle-mechanisms.md)。本节为接口约定，尚未进行平台行为验证。

## 页面可见的后端状态（已确认）

2026-09-28，用户接受以下六个公共状态，Windows 与未来 macOS 共用：

| 状态 | 含义 |
| --- | --- |
| `starting` | 正在启动，尚未就绪 |
| `ready` | 后端可用 |
| `stopping` | 正在正常清理 |
| `reclaiming` | 正在强制回收 |
| `failed` | 启动、运行或回收发生错误 |
| `stopped` | 已确认后端及所属进程全部退出 |

- `get_backend_state` 与 `backend-state-changed` 使用同一套状态定义，附带由 Rust 管理器计算的 `can_retry`。
- `failed` 本身不代表可以重试；旧后端及所属进程未确认回收时，`can_retry` 必须为 false。确认回收且未进入应用退出流程后，才允许按手动重试规则开放重试。
- 页面根据 `can_retry` 展示重试能力；Rust 在收到重试命令时仍校验当前状态，不能信任页面缓存。
- 状态载荷字段见下节；完整转换表仍待收敛，本节不表示实现已完成。

2026-09-28，用户接受查询与事件返回完全相同的状态字段：

| 字段 | 语义 |
| --- | --- |
| `state` | 上节定义的六个公共状态之一 |
| `revision` | 同一次 Tauri 宿主运行期间持续递增；后端重试不归零 |

## 失败清理后的状态转换（已确认）

- 运行期间不自动重载配置。
- 每次启动或手动重试重新读取配置；修正配置后可直接手动重试，无需退出整个应用。
- Rust 固定本次读取的 `backend` 配置，本次启动与退出均使用该组值，不因配置文件随后改变而更新期限。
- 在已有启动参数中增加 `--port`，由 Rust 将本次起始端口传给 Python；桌面托管模式以该参数为准。
- Python 仍通过 `--config` 指定的文件读取应用配置；上述约定固定的是后端托管配置，不宣称对整个配置文件进行原子快照。

## 重试成功后的页面恢复（已确认）

2026-09-28，用户接受以下页面恢复规则：

- 重试成功后，页面使用新 `base_url`，重新获取 Thread、消息和 Run 状态。
- 清理旧后端连接，忽略旧启动留下的迟到响应；旧请求结果不能覆盖当前启动的数据。
- 不自动重发用户消息，也不自动重新执行失败的 Agent 任务，避免重复执行工具或生成重复记录。
- 由前端统一 HTTP/SSE 客户端处理，Windows 与未来 macOS 共用。
- 本节规定页面重新连接行为，不改变已确认的启动恢复或手动重试规则。

## 启动超时后的清理时序（已确认）

2026-09-28，用户接受启动超时后仍给予正常清理机会：

1. 启动总期限耗尽时，停止就绪检查并记录启动超时，不再接受迟到的就绪结果。
2. 发送 `shutdown`，在已配置的正常退出期限内等待清理（默认 10 秒）。
3. 期限内未完成回收，则强制回收并使用固定 5 秒确认期限。
4. 确认所属进程全部回收后才允许手动重试；无法确认则保持禁止重试。

默认 60 秒启动、10 秒正常清理与 5 秒强制确认合计约 75 秒的等待预算，随后进入可重试的失败状态或回收未确认的失败状态；这不构成操作系统一定在该期限内完成退出的保证。配置修改时沿用本次启动固定的期限值。

## 后端主进程意外退出（已确认）

2026-09-28，用户接受 Python 主进程意外退出后立即处理所属残留进程：

- 主进程已退出，不能再依赖其接收 `shutdown` 或协调正常清理，因此不再等待 10 秒正常清理期限。
- 平台适配层检查所属进程，有残留则调用 `terminate_tree()`，最多等待 5 秒确认全部退出。
- 保留后端退出原因；确认全部回收后才允许手动重试，不自动重启。
- 无法确认回收完成时沿用已确认的失败处理，保持禁止重试并继续观察。
