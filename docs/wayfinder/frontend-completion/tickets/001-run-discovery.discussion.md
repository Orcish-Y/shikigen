# 确定会话 Run 发现与只读查询契约：讨论记录

本文件保留真实讨论的历史过程。票据已于 2026-10-03 关闭；最终确认见[决议](001-run-discovery.resolution.md)，完整契约以[会话与运行查询契约](001-run-discovery.contract.md)为准。

## 2026-10-03：用户选择会话列表作为发现入口

用户确认的方向：

- 首版不专门查询 active_run，使用 `/api/threads` 提供会话列表和状态。
- 用户同一时刻只打开一个会话；进入会话时，拉取历史消息或其他适当查询以获知该会话当前状态。
- `/api/threads` 改为分页列表，每页 20 条。
- 客户端定时轮询第一页，按会话 ID 对新结果与已加载列表去重。
- 列表按修改时间倒序。
- 面向普通用户统一使用“会话”“会话列表”，不直接显示 Thread。
- 会话列表展示当前状态，包括运行中、等待审批等，使用中文。

## 2026-10-03：用户确认保留最近运行的终态

用户选择保留“已完成／已取消／运行失败”，不在运行结束后统一显示“空闲”。会话状态由当前或最近一次运行的事实派生，等待审批的运行仍属于未终结任务。

## 2026-10-03：用户选择从历史消息定位最近运行

- 用户不希望历史消息响应增加 `latest_run`，倾向复用消息中的运行身份与状态。
- 用户提出的链路为：拉取历史消息 → 取最后一个 `run_id`，若状态为 `running` 则 GET Run stream → 从 `metadata.status` 读取状态。
- 当前消息响应仍未返回 Run 状态；候选补充是在消息记录外层增加查询时的 `run_status`，与已有 `run_id` 配对。该字段与工具消息 `content.status` 的成功／失败含义不同；不将可变化的运行状态写成消息创建时的持久事实。
- 观察接口也支持重建 `interrupted` Run 的持久事件，可恢复待审批请求；观察条件覆盖 `running` 或 `interrupted`，已通过后续交流确认。
- 历史查询与 GET stream 之间状态可能变化；取得 stream 后，以最新 metadata / lifecycle 收敛当前显示。

## 2026-10-03：用户认可等待审批的重建流程

用户以“行”认可前述等待审批恢复流程：

- 通过最后一个 `run_id` 调用 GET Run stream，恢复 `running` 或 `interrupted` Run 的观察；不增加 `latest_run`。
- 后端读取 Run、校验审批事实与 checkpoint，并回放 metadata 和持久事件；该机制已存在。
- 前端恢复消息、当前状态和仍有效的审批请求；按 seq 合并消息，避免历史生命周期覆盖当前状态。审批操作面板及提交仍待实现。
- 回放结束后保留“等待审批”；GET 不自动启动下一次 Agent 执行。用户提交全部审批响应后才继续执行同一个 Run。
- 上述确认属于恢复契约，未据此认领或解决后续审批、状态投影票据。

## 2026-10-03：用户确认游标分页

用户选择游标分页：

- 第一页不带游标，请求 `/api/threads`；每页固定 20 条，响应返回 `next_cursor`。
- 加载更多时将服务端返回的游标原样带回；定时轮询始终请求不带游标的第一页。
- 排序采用 `updated_at DESC, id DESC`，游标对应上一页末尾的位置。
- 游标降低普通页码受重排影响的问题，但按可变更新时间分页不承诺固定快照。严格一致性及列表合并规则仍需在最终契约中说明。

## 2026-10-03：用户确认轮询规则

用户认可以下规则：

- 窗口可见、后端就绪时，每 5 秒刷新会话列表第一页。
- 隐藏到托盘或后端未就绪时暂停；重新显示或后端恢复后立即刷新。
- 请求不重叠；上一轮未结束时不发起下一轮。
- 失败保留旧列表；成功按会话 ID 更新已有记录、去重，并按修改时间重新排序。
- 当前打开会话的实时状态继续通过 SSE 更新。

## 2026-10-03：运行详情查询说明与整体核对

用户以“行”认可运行快照和事件查询的说明。草案按前述建议列入两个新增 JSON GET 接口，最终接口范围和字段通过[契约草案](001-run-discovery.contract.md)整体核对，不凭这句回复推断全部字段已经确认。

## 2026-10-03：用户最终确认

完整契约草案已提交用户核对。用户回复“可以”，确认定稿；[决议](001-run-discovery.resolution.md)记录关闭及后续上下文。

## 定稿前的源码核对与待确认事项（历史）

以下保留当时的核对过程，原待确认事项已通过最终契约核对解决。

- 当前 `ThreadStore.list_threads()` 已按 `updated_at DESC, id DESC` 排序，但没有分页及 Run 状态。
- 当前会话消息查询只返回 message 事件，不包含完整 lifecycle / approval 事实。最后一条消息的 `run_id` 可用于定位候选 Run，不能单独证明其当前状态。
- 每个会话最多一个未终结的 Run；`running` 和 `interrupted` 均占用会话，后者等待审批。
- 合并轮询结果需要按 ID 更新已有记录并按修改时间重新排序；只忽略重复 ID 会丢失新的状态。当时待确定变动排序下的分页一致性及第一页之外的当前会话如何刷新。
- 定稿前待核对内容包括：无 Run 的展示、历史消息状态字段、分页与轮询边界、快照和事件查询、独立历史 Run 导航范围。具体结论统一见已确认契约。
- `RunService.read_run()` 在 `interrupted` 时会调用恢复校验，必要时可能持久化错误事实。若新增查询要求严格只读，需要明确与现有恢复校验的边界，不能直接把该方法称为无副作用查询。
