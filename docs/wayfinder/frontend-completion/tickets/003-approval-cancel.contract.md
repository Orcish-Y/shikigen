# 审批与取消交互契约

日期：2026-10-03。状态：用户已确认，前端行为待实施。

所属票据：[确定审批与取消的完整交互](003-approval-cancel.md)。最终确认见[决议](003-approval-cancel.resolution.md)，真实交流见[讨论记录](003-approval-cancel.discussion.md)。本文件统一记录该票据的完整契约，沿用已定稿的[会话与运行查询契约](001-run-discovery.contract.md)、[运行投影与恢复契约](002-run-projection.contract.md)和[当前设计规范](../../../../frontend/design.md)。

## 1. 做什么、为什么、用什么 API

**做什么：**在聊天时间线补齐逐项审批、参数查看、全部决策提交、请求核实与取消确认，使运行中和等待审批的任务都有完整操作路径。

**为什么：**现有后端已经支持这些操作，当前界面只有等待审批提示。操作必须绑定准确的运行和待审批请求，防止旧选择用于新请求，或把请求失败当成运行失败。

| 入口 | 用途与现状 |
| --- | --- |
| SSE approval required / resolved / invalidated | 已有；当前请求及审批历史的持久事实 |
| POST /api/threads/{thread_id}/runs/{run_id}/approval-decisions | 已有；提交全部当前决策，返回同一 Run 的 SSE |
| POST /api/threads/{thread_id}/runs/{run_id}/cancel | 已有；请求结束该 Run，返回 {data: RunSnapshot} |
| GET 同一 Run /stream | 已有；恢复观察，校验并重建当前暂停的审批 |
| GET 同一 Run 快照及 /events | 前置票据已确认的新增目标，尚未实现；纯读运行状态和持久历史 |

本票据不新增审批写接口，不增加参数编辑、批量批准、自动提交或取消原因字段。审批后继续执行仍是同一次运行；拒绝动作与取消整个运行分别呈现。

## 2. 架构位置与身份

| 部位 | 职责 |
| --- | --- |
| 运行事实投影 | 按前置契约提供当前状态、有效请求和历史事件 |
| 审批草稿 | 保存未提交选择、拒绝原因及所属请求，不作为已处理事实 |
| 操作记录 | 保存本次提交或取消的目标、提交内容、确认情况及 pending；防重入与结果核实 |
| BackendSession | 发送用户主动 POST，保留结构化错误，将返回 SSE 交给已有统一投影入口 |
| UI | 显示卡片、定位入口、参数详情、取消弹窗及当前操作反馈 |

- 草稿和操作记录由不随 Workspace 卸载的数据层维护；后端租约改变不能丢失输入。
- 请求身份包含 thread_id、run_id、checkpoint 的完整坐标、Interrupt ID 和 namespace。动作按 Interrupt 内的原始位置识别，不能用工具名称代替身份。
- 保存和恢复选择时核对全部 Interrupt、动作名称、完整 args、description 及对应 review_configs；对象键顺序不影响内容比较，数组顺序保留。
- 写请求捕获发起时的运行、请求身份、草稿版本与后端租约；选择、观察代次和租约过滤迟到结果。不能把旧响应应用到新会话或新 Run。
- 当前请求的有效性及 SSE 与查询的状态权威规则沿用前置契约；本地曾选中或曾提交不构成当前可操作身份。

## 3. 内嵌卡片与定位入口

- 每次 required 在所属 Run 的时间线位置呈现一张审批卡片，以事件 seq 排序和定位；卡片不伪造成普通聊天消息。
- 卡片内按服务端 interrupts 顺序分组，每组显示来源 namespace，再按 action_requests 原顺序展示动作。空 namespace 展示“主流程”，详情保留原始空值。
- 工具名称、服务端 description、允许的批准／拒绝控件保持可见；没有说明时标明未提供，不编造解释。
- 卡片显示“已选择 X / Y 项”。一个待审批请求的全部 Interrupt、全部动作选完才可提交，不拆成多个 POST。
- 每项默认未选择，使用互斥选择控件及中文标签“批准”“拒绝”；首版不提供全部批准／全部拒绝按钮。
- 只提供对应 allowed_decisions 允许且首版支持的选项。若当前格式无法完整解析，或某项没有受支持的决策，不开放整组提交，说明原因并保留查看、恢复和取消入口。
- 当前可操作卡片的 footer 放靛蓝“提交决策”和次要“取消运行”；提交未开放时显示未选完、正在核实、请求处理中或暂不支持等实际原因。
- 等待审批时底部主按钮为“处理审批”，工具栏也提供定位入口。点击滚动到当前卡片并将焦点移至卡片标题或首个未选择的动作，不代替用户作选择或提交。
- 运行中底部提供“取消运行”。核实时仍可定位已有只读卡片；无有效卡片时定位“审批尚未恢复”的提示和恢复入口，不生成空审批表单。

## 4. 参数和拒绝原因

### 参数默认折叠

- 每项参数默认折叠；“查看参数”展开完整格式化 JSON，“收起参数”仅改变显示。
- 长内容在现有代码区块内滚动，不截断原始参数，不让整个页面横向溢出。复制取得完整格式化 JSON，不包含行号或折叠提示。
- 提供“放大查看”，桌面复用 400px 右侧覆盖抽屉，窄屏复用现有底部面板。详情显示该动作的工具名称、来源、说明及完整参数，仅供查看与复制。
- 详情不提供参数编辑或另一套审批按钮。关闭、Esc、折叠导航和响应式变化不清空选择，不重新建立 SSE。
- 详情绑定打开时的请求和动作。请求被处理或运行结束后，可继续只读查看，并明确其为历史内容；切换会话或运行目标时关闭，不能随新请求静默换成另一项参数。

### 拒绝原因可选

- 选择拒绝时显示多行文本框，标明“拒绝原因（可选）”，允许留空。
- 临时切到批准时隐藏但保留原因，切回拒绝继续编辑。原因不进入批准的请求，也不作为已批准动作的历史说明。
- 纯空白原因可以不发送；非空原因按用户输入发送，不自动生成拒绝理由。
- 拒绝不会直接将 Run 置为 cancelled。提交后的运行结果继续由后端事实决定。

## 5. 保存、核实和历史状态

- 按应用命名空间和会话保存审批草稿、所属 Run／checkpoint／Interrupt／动作内容以及必要的未确认提交记录。选择不因折叠、参数层关闭、切换会话、宿主变化、刷新或重开应用丢失。
- 本地恢复先只读显示“正在核实审批”。只有 GET stream 正常完成全量回放、当前仍 interrupted、请求仍有效且身份与内容全部一致时，才恢复原选择并开放操作。
- 新 checkpoint、不同 Interrupt、namespace 或动作内容不复用旧草稿；新请求默认未选择。仅相同工具名称或相同参数不足以证明是同一请求。
- 本地 pending 在重新进入后变为待核实记录，不假定旧 HTTP 仍在请求，也不自动提交。
- 本地存储失败时回退应用内存，保留当前输入并显示“本地保存不可用”；不能因此改变 Run 状态。
- required 尚未核实、观察失败、缺少有效请求时只读。JSON events 可补历史，不代替 GET stream 的当前审批校验。
- resolved 展示服务端实际 decisions 和拒绝原因，标记“已处理”并锁定；不能用本地选择冒充服务端已接受的内容。invalidated 标记“运行已取消，审批失效”。
- 若只知道 Run 已终结但尚未取得对应审批事件，先提示运行已结束、不可再提交，不编造 resolved 或 invalidated。
- 服务端确认请求已处理、失效或 Run 已终结后，清理对应未提交草稿及待核实记录；已处理历史来自事件。操作清理检查身份，不能清空新的审批草稿。
- 404 时不把草稿改绑到其他会话或请求；保留本地输入供核对或复制，禁止提交。

## 6. 提交和 pending

### 提交条件与数据

提交需宿主 ready、当前会话和 Run 身份正确、当前请求已经恢复校验、全部动作均有允许的决策，且同 Run 无另一项写请求 pending。若之前结果待确认，必须已经完成当前事实核实；该操作的重试等待到期后才能再次发出。

POST body 沿用现有 `{responses: {InterruptID: {decisions: [...]}}}`。responses 必须覆盖全部当前 Interrupt，decisions 保持动作顺序；批准只含 type，拒绝可含 message。示例仅说明现有数据形状：

```json
{
  "responses": {
    "interrupt-a": {
      "decisions": [
        {"type": "approve"},
        {"type": "reject", "message": "请改用不会覆盖已有文件的操作"}
      ]
    },
    "interrupt-b": {
      "decisions": [{"type": "reject"}]
    }
  }
}
```

前端 checkpoint 用于身份保护；当前 API body 不发送 checkpoint，不新增客户端请求标识，也不声称服务端已经提供该字段的条件提交。

### 请求确认前互斥

- 发出审批后捕获完整提交内容，显示“提交中…”，锁定本组编辑、提交和同 Run 的取消，避免本次请求期间内容变化或重复请求。
- 发出取消后显示“取消中…”，同 Run 审批编辑、审批提交和再次取消不可用。
- pending 不是持续 SSE 的寿命。审批收到本次 POST 的有效 metadata、核对同一 Run 后确认接收并结束请求 pending；后续 SSE 作为观察连接继续运行。旧请求或 GET 的 metadata 不能作为本次 POST 接收确认。
- 若此前已确认该 Run 终态，迟到的 running metadata 不能让它回退。收到可信终态时，立即使旧审批不可操作。
- 取消收到有效快照后结束请求 pending；取消快照的状态处理见第 8 节。
- 提交内容在接收确认前保留；接收后卡片只读，等待实际 resolved 等事实，不将 HTTP 200 或本地点击直接绘制成已处理事件。
- 请求失败或被主动中止后结束实际请求 pending，进入相应错误／待核实反馈；先 GET 核实事实再恢复写操作，不留下永久“提交中”的假请求。
- 切换会话、隐藏窗口和租约撤销仍按前置契约中止观察。中止未确认 POST 不撤销服务端动作；保留目标和提交记录，重新进入只做 GET 核实。

## 7. 提交失败与结果核实

已有 GET 重试、Retry-After、请求失效和错误分类沿用前置契约，不新增一套循环重试。所有 POST 都需用户主动，不自动重发。

| 情况 | 展示和恢复 |
| --- | --- |
| 409 | 提示审批已变化，GET 同一 Run 重建；以当前实际身份与 decisions 为准 |
| 422 | 保留选择和原因，显示实际校验信息；仅在后端提供定位时标出具体项，GET 核实后允许修正 |
| 503 | 提示暂不可确认／处理，遵守 Retry-After，GET 核实；不自动再 POST |
| 接收确认前网络故障、POST 500、解析失败或主动中止 | 显示“审批提交结果待确认”，保存提交内容，GET 同一 Run；不宣称决策未被接受 |
| 已确认接收后断流 | 审批已经接收，只恢复 GET 观察，不重新开放旧决策 |
| Run 404 | 停止自动恢复，提示运行不可读取；可重新查询会话，原选择只读保留 |

恢复后的具体处理：

- 同一请求仍 interrupted 且通过全量校验：恢复选择和编辑，显示当前仍等待这组决策。若先前结果未知，不能由一次查询断言旧请求绝不会稍后生效；用户可主动“重新提交决策”，再次按原身份校验与当前选择提交。
- 原请求 resolved：显示后端实际决策，结束旧提交的待核实状态；不能仅凭与本地内容相同就声称是本客户端完成的。
- 原请求 invalidated 或 Run 终态：锁定旧请求，展示真实结果。
- 已换成新请求：旧选择不带入，新动作重新选择。
- 查询失败或审批未完整恢复：保留选择只读，提供查询／重新连接入口，按前置上限恢复；不开放盲目重发。

一次 GET 的结果只能说明查询时刻的事实。手动重新提交仍可能遇到原请求或其他请求先被接受而返回 409；界面继续收敛实际事实，不自动改写已提交决策。

## 8. 取消确认、结果与竞态

### 确认弹窗

- 对当前已知 running / interrupted Run 提供取消。取消不依赖审批参数层是否展开，也不要求审批草稿选完或审批表单可解析。
- 同 Run 有写请求 pending，或结果待确认后的当前事实尚未核实时，暂不可取消；GET 核实运行身份与状态后再恢复。只读状态查询足以核实取消目标，不能因此开放未经恢复校验的审批提交。
- 每次用户点击取消先显示一次原生 dialog，复用现有白底、细边框、标题条和遮罩，宽度沿用现有普通弹窗，不使用系统风格之外的警告页。
- 标题“取消本次运行？”，显示所属会话。说明“取消不会撤销已经发生的工具操作，已开始的操作也不保证立即停止。”
- 按钮“继续运行”与“确认取消”。初始焦点在继续运行；确认使用已有危险语义色，Esc、关闭和遮罩关闭均不发 POST。不提供记住并跳过确认。
- 确认瞬间重新检查原 thread_id / run_id、当前选择、租约和操作可用性；切换会话、目标改变、隐藏或宿主失效时关闭确认，不能把确认意图带到另一个任务。
- 确认期间若已获得终态，关闭或转为结果提示，不再请求取消。发出 POST 后关闭弹窗，将 pending 显示在该 Run 的操作区；随后关闭其他详情不撤销请求。

### 返回快照是写操作结果

取消响应的 RunSnapshot 使用 id，边界处与 SSE run_id 对齐，并核对 thread_id。有效响应表示后端已经确认该 Run 的结果，区别于可能过期的普通查询响应。

| 返回／核实的终态 | 处理 |
| --- | --- |
| cancelled | 显示“已取消”，锁定当前审批，结束取消 pending／待核实记录 |
| completed | 显示“已完成”，说明运行已经完成；不改写成已取消 |
| error | 保留“运行失败”及实际错误；不覆盖为已取消 |

- 同一 Run 的有效取消终态响应可立即收敛卡片、输入区和会话状态，不等待旧 SSE 的下一帧。既有终态不被迟到的非终态帧覆盖。
- 响应只作用于它的目标 Run，不能改写后来选中或新创建的 Run；旧选择／租约失效的回调仍按前置契约过滤，重新进入以 GET 确认。
- 响应身份不符、无法解析或意外返回非终态时，按协议问题保留已知事实并 GET 核实，不显示“已取消”，也不自动再 POST。
- cancelled 表示取消事实已提交，不保证工具协作停止已全部完成。已有完整消息和工具结果继续保留。
- 取消确认后按需 GET events 补齐真实 invalidated 和生命周期记录；不依赖客户端伪造审批事件。用量待结算与详情事件补读依已确认的[运行详情契约](005-run-details.contract.md)，实现待完成。
- 若已有同 Run 的 running 观察，保留其收尾以取得最后事实；已知终态后的正常 EOF 或主动停止不触发意外 running EOF 恢复。需要补历史时使用前置 GET 规则。

### 请求失败与竞争

- 取消网络故障、POST 500 或中止时显示“取消结果待确认”，GET 快照／观察核实，不自动 POST。503 遵守 Retry-After，404 停止并提示目标不可读取。
- GET 确认 cancelled / completed / error 时以实际终态结束待核实，不把未收到取消 HTTP 响应当作取消失败。
- GET 仍为同一非终态时，可以恢复手动取消入口；再次点击仍需确认，并遵守重试等待。说明上次结果未确认，不断言它没有生效。
- GET 失败时保留当前事实和输入，提供手动查询；不把取消故障写成 Run error。
- 本客户端请求确认前互斥；其他客户端或运行自然结束仍可能竞争。后端已提交结果决定状态，前端不覆盖服务端的第一次有效终态，也不自动撤销或再次提交审批。

## 9. 样式、焦点与状态反馈

- 审批卡片沿用工具区块的 8px 圆角、1px 边框与现有宽度，琥珀只用于等待提示；正文白底或 Slate 浅灰。提交用靛蓝，取消为次操作，确认弹窗使用既有危险色扩展。
- 正文及决策按钮不使用微小徽标字号，关键控件至少 14px；触控目标至少 44px。动作较多时卡片正常占据时间线，不用固定悬浮按钮遮挡最后内容。
- 选择控件有分组名称、选中状态和键盘操作；拒绝原因与对应动作关联。错误贴近本次操作，保留已有 business-notice 的样式，不只依赖 toast 或颜色。
- 参数层、取消弹窗和运行详情同一时刻只保留一个前景模态，避免多层焦点约束；关闭后将焦点返回仍存在的入口，否则返回当前工作区的稳定位置。
- 当前请求被处理时及时说明可操作性变化；状态以适量 aria-live 播报，不逐条重复播报全部历史。
- 布局折叠和关闭详情不改变数据与观察身份。全局滚动、键盘／IME、窄屏导航和四档视口的最终验收继续由交互票据统筹。

## 10. 实施衔接与后续范围

- 前端需补齐 BackendSession 的审批／取消调用、审批载荷解析、按请求绑定的草稿与操作记录，以及上述卡片、详情和确认 UI；不把取消仅实现为 AbortController。
- 后端继续使用现有审批与取消写接口，不新增隐式自动恢复执行。后续已确认的[消息、工具、导出与本地资源契约](004-message-tools-export.contract.md)要求在现有取消／失败结算中原子保存已接入正文；取消成功快照需与保存结果一致。这属于新增结算能力，不新增取消端点；只读 Run 查询依前置契约实施。
