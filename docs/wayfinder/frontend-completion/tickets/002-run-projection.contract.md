# 运行投影与恢复契约

日期：2026-10-03。状态：用户已确认，接口与前端行为待实施。

所属票据：[确定运行投影、观察连接与错误恢复](002-run-projection.md)。最终确认见[决议](002-run-projection.resolution.md)，真实交流见[讨论记录](002-run-projection.discussion.md)。本文件统一记录该票据的完整契约；前置 HTTP 数据形状以已确认的[会话与运行查询契约](001-run-discovery.contract.md)为准。

## 1. 做什么、为什么、用什么 API

**做什么：**将持久运行事实、临时流式预览、观察连接和用户未提交输入分别维护，使当前会话可以重连、切换和恢复，同时正确处理迟到结果与发送结果未知。

**为什么：**当前前端已接入消息与 SSE，但连接与运行状态混在少量字段内，审批和完整事件没有形成投影；发送草稿过早清空，Workspace 卸载还会丢失内存输入。

**用什么 API：**

| 入口 | 用途 |
| --- | --- |
| GET /api/threads | 每页 20 条、第一页可见时每 5 秒轮询；发现会话摘要变化 |
| GET /api/threads/{thread_id}/messages | 读取完整历史，定位当前或最近发起 Run |
| GET /api/threads/{thread_id}/runs/{run_id}/stream | 全量重建并跟随；自动恢复及手动重连 |
| GET Run snapshot / events | 纯读状态、用量、错误、时间及完整持久事件；新增目标，尚未实现 |
| POST Thread stream / Run approval-decisions | 用户主动发送或提交审批，消费返回的 SSE；不自动重发 |
| POST Run cancel | 用户主动取消；返回快照及竞态交互见已确认的[审批与取消交互契约](003-approval-cancel.contract.md) |
| 现有宿主状态桥接 | ready、startup_id、base_url 及启动重试，继续沿用 |
| 窗口可见状态桥接 | 新增输入，触发隐藏暂停和显示恢复，见第 12 节 |

新增能力继承[当前设计规范](../../../../frontend/design.md)：中文状态、既有浅色提示区、细边框和靛蓝操作，不新增独立恢复页面或运行追踪页面。

## 2. 架构位置与数据归属

| 部位 | 负责维护的内容 |
| --- | --- |
| 宿主状态 | 是否可以请求当前后端，以及本次启动身份；不代替观察状态或 Run 状态 |
| BackendSession | 地址租约、请求取消、结构化 HTTP 错误、SSE 解析；租约失效后旧结果不能写入 |
| 会话数据 | 列表和分页进度、当前选择、按会话保存的完整消息、各 Run 的事件和最近已知快照 |
| 当前观察任务 | 唯一的当前观察连接、重建中的临时预览、重试次数和计时器 |
| 本地输入记录 | 每个会话的草稿版本、提交原文及接受情况，独立于观察连接和 Workspace 生命周期 |
| UI | 从上述数据派生状态、提示及按钮可用性；不从 EOF、HTTP 错误或工具失败猜测 Run 结果 |

草稿和会话数据的所有者不能放在随宿主非 ready 而卸载的 Workspace 内。可以保留既有宿主启动/故障界面；已读事实在应用内存中保留，重新进入工作台后再查询。前端刷新后完整历史从服务器读取，本地持久保存范围见第 9 节。

## 3. 身份与失效规则

- 请求绑定当前 BackendSession 的 startup_id、base_url 和 AbortSignal；宿主撤销租约后全部旧请求失效。
- 消息与选择按 thread_id 隔离；快照、事件和预览按 thread_id / run_id 隔离。
- 当前选择和每次观察均记录各自的代次。切换、重新建立观察或新 Run 成为目标后，旧回调和旧计时器不能发布结果。
- JSON 请求记录其开始时的运行身份和状态更新计数；返回时检查是否仍适用。取消 HTTP 请求和检查身份共同防止迟到结果污染。
- 列表分页进度与当前选择独立。第一页轮询更新摘要，不改变选择、草稿或已建立的加载更多游标。
- 失效的 GET 不算恢复失败；失效的 POST 观察不能撤销已提交任务。尚未取得本次 run_id 时，将提交记录保留为结果待确认。

身份隔离不靠比较 UUID 大小。消息与事件的 seq 属于会话顺序，允许空洞，不把不连续当作丢失。

## 4. 打开会话与发现新 Run

1. 窗口可见、宿主 ready 后，读取当前会话的完整历史；已有缓存可先显示，并标明正在更新。
2. 成功的空历史表示该查询时刻尚无 Run；读取失败或未读取不能当成空会话。若同时已有更新的 Run 线索，重新读取以收敛。
3. 取末条消息的 run_id / run_status。running 或 interrupted 建立 GET stream；终态先展示完整消息，按需要读取 JSON 快照和事件。
4. 本地保存的选中会话与 run_id 只提供恢复线索，必须用新的服务端查询确认归属及当前状态。
5. 第一页轮询发现当前会话的不同 run_id 时，先刷新历史核实运行身份，再切换观察目标；不把迟到的旧摘要直接当成新 Run。
6. 当前 Run 改变后关闭旧观察，不调用 cancel；新身份从其自己的状态、用量和审批事实开始，不继承前一个 Run 的值。

已确认的会话终态中文继续保留“已完成”“已取消”“运行失败”。只有确实尚无 Run 才显示“未开始”。

## 5. 完整消息、临时预览与持久事件

- 保存完整公开消息记录，不在接入层丢失 message_id、content blocks、tool_calls、artifact、工具状态或原始事件字段。后续呈现由消息票据决定。
- 完整历史和 SSE message 事实按会话 seq 合并、排序、去重；完整消息覆盖同 seq 的临时预览。重复完整事实不新增一行。
- delta 只是当前观察内的追加片段，不把同 seq 的 delta 当作重复完整事实丢弃，也不按文本内容去重。
- 每次新 GET 观察成功建立并取得有效 metadata 后，仅清空目标 Run 未提交的预览，使用空缓存积累本次回放 delta。其他 Run 和已提交消息继续保留。
- 等待重连、请求在取得有效 metadata 前失败时，原有内容继续显示；旧预览不是新的完整事实。
- JSON events 与 SSE event 使用同一公开结构，按 thread_id / run_id / seq 合并。审批与生命周期保留在事件投影中，不伪造成普通聊天消息。
- JSON 查询只返回截至该次查询已提交的事实；不因某事实没有出现在一次结果中就删除已读的完整事实。

后续已确认的[消息、工具、导出与本地资源契约](004-message-tools-export.contract.md)确定 Markdown、工具关联、artifact 和已提交导出，并补充取消／失败时后端原子保存生成正文及终态消息补读。预览不会由前端自行变成已保存事实；应用实现仍待完成。

## 6. SSE 与查询的状态合并

### 当前状态

- 当前会话有有效观察时，以 SSE metadata 更新该 Run 的当前状态，并同步列表中同一会话、同一 Run 的显示状态。
- 列表轮询、历史消息附带状态或 JSON 查询不覆盖正在观察的同一 Run 状态。历史 lifecycle 作为过去的事实保留，不覆盖 metadata 当前状态。
- 没有有效观察时，允许新发起的查询更新状态；若请求期间已有新 metadata、目标改变或租约失效，不接受它带回的旧状态。
- 同一 Run 已确认的终态不回退为非终态。interrupted 可以继续为 running，不能把所有状态排列成固定的新旧顺序。
- 列表 updated_at 按服务端事实合并，不以本地当前时间伪造更新时间；较旧摘要不能回退已知时间。SSE 未提供更新时间时，状态立即更新，排序等待服务端摘要补齐。

### 快照的其他字段

- metadata 是部分更新：仅实际携带的字段更新投影，省略字段不自动清空已有值。明确的 usage=null 表示未知，不显示为零；usage_pending 缺少或未知不解释为 false。
- 值保留同时保留其来源和是否重新确认。审批继续等新执行阶段开始时，前次已结算标志不能当成本阶段已经结算；此前累计用量仍可阅读。
- JSON 快照补齐错误、时间、用量和结算情况时，检查运行身份及请求期间相应事实是否已更新；被淘汰的结果不能覆盖新字段。
- 正常观察结束后补读 JSON 快照；用量仍待结算时的后续刷新、读取上限与显示细节依已确认的[运行详情、用量与事件契约](005-run-details.contract.md)，应用行为待实施。

## 7. 观察连接状态与 EOF

| 状态 | 中文含义 |
| --- | --- |
| idle | 未建立观察，例如尚无 Run |
| connecting | 正在连接或重建；尚未取得有效 metadata |
| open | 观察连接已建立，不表示任务完成或服务健康 |
| retry_wait | 观察中断，显示自动重连倒计时和次数 |
| closed | 正常回放/观察结束；保留后端确认的 Run 状态 |
| paused | 因窗口、选择或宿主生命周期暂停观察 |
| failed | 自动恢复已停止，显示原因和手动恢复入口 |

具体名称可以由实现调整，但宿主、连接和 Run 状态必须分别表达。

- 最后确认状态仍为 running 的意外 EOF 属于观察失败，进入 GET 恢复。
- interrupted 的正常全量回放结束后，保持“等待审批”，不因 EOF 再次不断连接；审批是否可操作见第 10 节。
- completed / cancelled / error 的正常 EOF 不报连接故障，不改成其他运行结果。
- 流内 error 或解析失败不能因为后续 EOF 而被吞掉，按第 11 节处理。
- 长工具执行没有 delta 不等于断流，不设置“没有文字输出就失败”的判定。

普通发送需要宿主 ready、当前状态已确认、没有提交 pending 或发送结果待确认，并且当前 Run 不为 running / interrupted。2026-10-04 已在[交互与验收契约](006-interaction-acceptance.contract.md)确认执行期间可以编辑并保存下一条草稿，结束后手动发送，不排队、不自动发送。

## 8. 自动 GET 恢复与生命周期

### 重试

原观察失败后，按以下顺序等待并尝试：

| 自动尝试 | 等待间隔 |
| --- | --- |
| 第一次 | 1 秒 |
| 第二次 | 上一次失败后 2 秒 |
| 第三次 | 上一次失败后 5 秒 |

503 等待时间不早于 Retry-After 指定的时间；没有有效值时沿用本地间隔。第三次仍失败则进入 failed，保留数据，提供“重新连接”或“查询状态”。

- 一个恢复轮次只有一个 GET 任务；error 与随后的 EOF 不重复计数或安排两次恢复。
- 收到首帧 metadata 不立即重置连续失败次数，避免同一错误反复回放形成无限循环。观察连续建立 30 秒未发生故障，或正常完成 interrupted / 终态回放后，才重置连续失败计数。
- 三次失败后，周期性列表轮询不能不断重新开启同一 Run 的恢复轮次。手动重连、重新打开会话/显示窗口，或新的有效后端租约可开始新轮次。
- 手动入口与自动恢复复用同一任务，并遵守未到期的 Retry-After；已有连接或请求 pending 时不并发重复连接。
- 不使用 query cursor 或 Last-Event-ID，不自动重发任何 POST。

### 暂停与重新进入

- 切换会话、隐藏到托盘或后端未就绪时，关闭旧 SSE，取消相关 GET 与计时器，保留输入及完整事实；不调用取消任务接口。
- 重新选中会话、窗口显示或后端 ready 后，立即 GET 历史重新定位，并按第 4 节恢复。多个同时到达的触发信号合并为一次恢复。
- 仅失去焦点不暂停。缩放侧栏、打开详情、关闭参数层、调整响应式布局不改变当前观察身份。
- 列表轮询继续沿用前置契约：可见且 ready 时每 5 秒，不重叠；隐藏或未就绪时暂停。

## 9. 草稿、提交接受情况与本地保存

### 发送的状态

| 情况 | 处理 |
| --- | --- |
| 发出 POST，尚未确认接受 | 保存提交原文及草稿版本，显示发送 pending，防止重复点击 |
| 收到本次 POST 的有效 metadata | 取得新 run_id，确认接受；仅清空仍对应此提交的草稿，不覆盖用户后来改写的内容 |
| 明确的输入校验失败或冲突 | 保留原文，按该操作错误修正或查询；不自动重发 |
| 尚未取得本次 run_id 即断连、POST 500 或接受情况不明 | 保留为“发送结果待确认”，只做 GET 查询 |
| 已取得 run_id 后断流 | 发送已接受，转为已知 Run 的 GET 恢复，不把原文自动放回发送队列 |

旧 Run 的 metadata、查询成功或相同消息文本不独立证明本次 POST 被接受。当前接口没有客户端请求标识，本轮不新增请求关联或自动重发契约。

### 结果待确认的操作

- 自动读取该会话历史，恢复当前实际 Run 和消息；查询暂未发现新任务时仍保留待确认状态。
- 提供“查询状态”。展示可供核对的最新用户消息和运行事实，用户明确确认对应发送后可以结束待确认记录；清空原文仍遵守草稿版本规则。
- 用户也可以主动选择“作为新任务发送”。说明该动作会发起新任务；当前会话 running / interrupted、后端未就绪、状态尚未核实时仍不可发送。
- 旧 POST 观察被主动中止时，已有接受确认不撤销；还没有确认时保留待确认记录。应用重新进入后，遗留的提交 pending 不能当成仍有有效请求，按待确认流程处理。

### 保存范围

- 以应用自身命名空间、会话 ID 在本地存储保存草稿、版本、未确认提交原文及必要记录；选中会话和已知 run_id 仅作为恢复线索。
- 恢复文字不恢复执行。Run 状态、完整历史、可提交审批身份从 GET 重新确认。
- 动态端口、startup_id、AbortController、计时器、delta 和连接状态不持久恢复为当前有效状态。
- 本地存储不可用或写入失败时，回退为应用内存并提示“本地保存不可用”；当前文字保留，不因保存故障丢弃输入或改变 Run 状态。
- 会话已不存在时保留未发送文字供用户复制或转到新会话，不静默删除草稿。

## 10. 当前审批的投影

- GET stream 回放中按 seq 处理 required / resolved / invalidated，按运行、checkpoint 坐标和 Interrupt 身份确定当前请求。
- 回放从当前观察的事实重新构建有效请求，不把旧卡片直接恢复为可提交。已展示卡片可以只读保留，同时显示正在核实。
- 当前 metadata 为 interrupted、全量回放正常结束且存在仍有效的 required 后，才开放该请求的审批操作。JSON events 查询可补历史，不能替代 GET stream 对当前暂停的恢复校验。
- running 或终态的历史审批不开放提交。resolved / invalidated 使对应请求失效，新 checkpoint 不复用旧审批的可提交身份。
- 缺失有效请求或观察失败时显示“审批尚未恢复”，按恢复策略处理；不猜测动作或将 Run 改为 error。
- 同一身份的有效请求可保留原选择；动作、长参数、拒绝原因、选择持久保存、提交 pending 与取消竞态以已定稿的[审批与取消交互契约](003-approval-cancel.contract.md)为准。

## 11. 错误与恢复动作

客户端保留 HTTP status、detail、Retry-After，以及 SSE error 的 code、message、recoverable。列表、历史、观察、提交和宿主错误归属各自操作。

| 情况 | 动作 |
| --- | --- |
| 网络故障、GET 503、可恢复 SSE error | 自动恢复 GET，遵守三次上限及 Retry-After；保留最后确认状态 |
| POST 503 或传输失败 | 仅 GET 查询接受情况和当前事实，不自动重发 POST |
| 创建会话 POST 的结果未知 | GET 会话列表供用户核对，不自动再次创建，不改变原选中会话的草稿 |
| 404 | 停止自动重试。Thread 读取 404 展示会话不存在和返回列表入口；Run 404 展示运行不可读取，可重新查询会话，不能直接删除整个会话 |
| 发送 409 | 保留输入，GET 历史定位实际当前 Run |
| 审批 409 | GET 同一 Run 重建；按实际有效审批身份决定选择是否仍适用，不自动提交 |
| 列表游标 422 | 保留列表，提供显式重新加载；重新从第一页建立分页位置 |
| 输入或审批 422 | 保留内容、展示当前操作的校验问题；后端未提供定位信息时不编造哪一项出错 |
| GET 500、不可恢复 SSE error、协议解析失败 | 停止自动重试，保留完整事实与状态，提供手动查询/重连 |
| POST 500 | 可能已接受，保留记录并 GET 查询；不直接提示任务肯定没有执行 |
| GET stream 400 | 请求协议不兼容，停止自动重试，不默默加/改游标参数 |
| Run error 状态或匹配的 lifecycle error | 展示后端已确认的“运行失败”、错误及 code；不是连接故障 |
| 主动 Abort / 租约撤销 | 暂停或失效，不报网络故障，不消耗重试次数，不取消后台 Run |

列表每 5 秒轮询不再叠加额外三次重试任务；503 的 Retry-After 会推迟下一次轮询。JSON 500 不自动把数据库 Run 改成 error。HTTP 故障也不触发宿主自动重启。

## 12. 实施衔接与待补接口

### 前端与现有后端

- BackendSession 适配已确认的分页/消息状态/快照/事件目标，保留结构化错误，并将 POST 返回和 GET 恢复的四类 SSE 帧送入同一投影入口。
- 会话数据与输入记录独立于 Workspace 的挂载及 BackendSession 寿命；当前观察任务使用租约、选择、运行与代次检查写入。
- 后端纯读 JSON、GET stream 恢复校验、运行事实提交和取消语义均沿用前置契约，不增加自动审批、自动取消、任务自动续跑或请求标识。

### 窗口可见状态桥接目标

当前宿主在桌面入口中调用 window.hide / show，但前端没有对应输入。已确认新增桥接为：

| 入口 | 目标形状 |
| --- | --- |
| get_workspace_visibility | 返回 {revision, visible} |
| workspace-visibility-changed | 推送相同 {revision, visible} |

revision 在当前宿主生命周期中递增。前端先订阅、再查询，按 revision 接受更新，避免初次查询覆盖新事件。visible 表示主窗口已显示；焦点变化不当作隐藏。状态依据成功的窗口操作和实际状态更新，不因失败的 hide/show 命令假定窗口已变化。

该桥接为已确认暂停行为提供输入，尚未实现；后端进程退出、托盘重试和 startup_id 继续沿用既有契约。宿主可见状态获取失败时保留最近已知值；首次未知按可见处理，避免因此永久阻塞工作台。
