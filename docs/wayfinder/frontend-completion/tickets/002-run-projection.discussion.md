# 运行投影、观察连接与错误恢复：讨论记录

日期：2026-10-03。所属票据：[确定运行投影、观察连接与错误恢复](002-run-projection.md)。

状态：已结束，用户最终回复“可以”，确认[运行投影与恢复契约](002-run-projection.contract.md)定稿；最终结论见[决议](002-run-projection.resolution.md)。本文件保留讨论历史，早期待细化内容以定稿契约和后续票据为准，不表示应用已经实现。

## 1. 本轮核实的事实

- 当前前端已有按会话 seq 合并消息、完整消息覆盖 delta 预览、metadata 合并运行状态，以及后端启动身份失效后撤销旧请求的基础。仍缺少独立观察连接状态、自动恢复调度、审批投影和结构化 HTTP 错误。[会话状态管理](../../../../frontend/src/useConversations.ts)、[HTTP/SSE 客户端](../../../../frontend/src/backend-client.ts)。
- 当前 SSE 客户端正常读到 EOF 后直接返回；选中会话的 GET 观察异常只显示读取失败，没有专用重连调度。发送流结束后会触发 GET 刷新，不自动重发 POST。[会话状态管理](../../../../frontend/src/useConversations.ts)、[HTTP/SSE 客户端](../../../../frontend/src/backend-client.ts)。
- 后端 GET Run stream 全量重建，不接受查询参数或 Last-Event-ID。running 时可跟随本地执行；interrupted 或终态通常回放持久事实后结束。[Run 路由](../../../../app/routes/run.py)、[观察重建](../../../../packages/harness/shikigen/runtime/run_observation.py)。
- 观察资源关闭只回收订阅，不调用取消运行。取消运行有独立 POST 接口。[Run 路由](../../../../app/routes/run.py)、[观察重建](../../../../packages/harness/shikigen/runtime/run_observation.py)。
- SSE `error` 的公开语义是观察失败；它与 Run 的 error 状态不同。已知本地执行不可观察时 GET stream 返回 503，并带 Retry-After: 1。[SSE 公开契约](../../../../app/run_contract.py)、[Run 路由](../../../../app/routes/run.py)。
- 当前执行的 Stream 订阅会回放完整内存事件，包括 delta。多个 delta 可属于同一条消息、共用该消息的 seq，不能按 seq 把每个 delta 当独立事实去重；全量重建时不能继续向旧预览追加回放文字。[本地流](../../../../packages/harness/shikigen/core/stream.py)、[消息预览接入](../../../../packages/harness/shikigen/runtime/run_events.py)。
- 后端发起 Run 时在同一事务中提交运行身份、running 事实和首条用户消息；POST 发送流返回该次运行的 metadata 后，可以确认这次发送已被接受。当前前端在 send() 同步返回请求已发起时就清空草稿，早于这个确认时刻。[运行创建](../../../../packages/harness/shikigen/runtime/runs.py)、[发送入口](../../../../frontend/src/App.tsx)。
- 当前 App 在宿主不为 ready 或 BackendSession 不可用时返回启动/故障界面，卸载 Workspace；草稿保存在 Workspace 的组件状态内，后端状态切换会丢失这部分输入。Workspace 还以 startupId 为 key，新启动会重新挂载。[应用入口](../../../../frontend/src/App.tsx)。
- 原 PRD 要求提供手动重新连接；离线后由用户恢复全量观察。本轮用户已确认调整为自动 GET 恢复，并保留手动入口；完整细则仍在讨论。[PRD：流式与错误恢复](../../../frontend/frontend-prd.md)。

## 2. 已确认：意外断流后自动恢复观察

用户选择：自动 GET 恢复，并保留手动重连入口。

已知 run_id 时，SSE 意外断开后自动调用 GET Run stream 全量重建。只重试 GET，不自动重发发送或审批 POST；等待审批及终态的正常 EOF 不触发重连。

重试次数、节奏、停止条件及恢复时的投影合并仍需后续逐项讨论。

## 3. 已确认：自动恢复连续失败时的重试策略

用户确认：从原观察失败后，按 1 秒、2 秒、5 秒的等待间隔自动重试 GET，最多尝试 3 次。仍失败则暂停自动恢复，保留已显示内容并提供手动重新连接。503 的等待时间至少遵守 Retry-After，不提前发出请求。

未采用持续自动重试。哪些错误可以重试、何时暂停和重新建立观察仍待细化。

## 4. 已确认：全量重建时保留完整消息并重建预览

用户确认：新观察成功建立并取得有效 metadata 后，保留已提交的完整消息，仅清空该 Run 尚未提交的流式预览。新一轮 delta 从空缓存积累，不追加到上一次观察的预览；完整消息到达后按会话 seq 替换预览。

等待重连或请求在建立新观察前失败时，原有内容继续显示。此规则避免全量回放导致文字重复，并使完整历史不因重连而闪空。审批投影和状态来源竞争仍另行讨论。

## 5. 已确认：SSE 与查询响应的状态优先级

场景：列表或 JSON 查询先发起，之后 SSE 收到 completed，较早查询最后才返回 running。当前 metadata 没有与 JSON/列表共用的版本号，不能仅按响应到达顺序覆盖状态，也不能把各状态排成固定优先级；interrupted 可以继续变回 running。

用户确认：当前会话的有效 SSE metadata 为状态来源，并同步会话列表中对应运行的显示状态。列表轮询或 JSON 查询不覆盖正在观察的同一 Run 的状态；其他会话继续按列表结果更新。

没有有效观察时，允许新发起的查询补充状态。查询需记录其开始时的运行身份和本地状态更新代次；返回前若已有新 metadata 或观察目标改变，则不接受该查询带回的状态。同一 Run 已确认的终态不回退为非终态；不同 Run 不按状态文字判断新旧。

列表发现不同 run_id、正常等待审批回放结束后的状态同步，以及用量等非状态字段的合并仍需细化。

## 6. 已确认：草稿清空以发送被接受为准

用户确认：发出 POST 时保留原始草稿及该次提交对应的草稿版本；取得这次 POST 的有效 metadata、确认新 Run 已建立后，才清空仍属于该次提交的草稿。若用户已经改写输入，不清空或覆盖后来的新草稿。

HTTP 失败或尚未取得此次 run_id 时，保留原文；结果未知时仅通过 GET 读取会话事实，不自动重发 POST。旧 Run 的 metadata 或普通历史查询成功不作为此次发送已被接受的证明。没有请求身份可以对应时，不能仅凭历史中存在相同文本就自动清空草稿。

结果未知时如何恢复操作可用性、是否需要人工确认匹配的历史消息，以及本地持久保存范围仍需后续讨论。

## 7. 已确认：没有 run_id 时先查询，仍不明确则由用户核对

当前 ChatRequest 只有 message 及可选 thread_id，没有客户端请求身份；后端生成 Run 和入口消息身份。GET 历史暂未查到新任务，不足以证明原 POST 一定没有被接受；相同消息文本也不能独立证明对应关系。[发送路由](../../../../app/routes/run.py)、[运行创建](../../../../packages/harness/shikigen/runtime/runs.py)。

用户确认采用推荐方案：未取得此次 run_id 就发生连接故障时，保留草稿并显示“发送结果待确认”，自动 GET 会话历史恢复当前事实。发现新 Run 后，按已有查询契约读取状态并恢复观察；它是会话当前事实，不直接证明原 POST 的接受结果，不据此自动清空草稿。

仍不明确时提供“查询状态”，不自动重发 POST，也不把一次空查询当作发送失败。普通发送保持受结果未知状态约束；用户核对后，可以显式选择将保留草稿作为新任务发送，该动作不是安全续传。当前会话存在 running / interrupted Run 时仍禁止发起新任务。

本轮不增加客户端请求标识或服务端关联查询。具体核对入口与本地保存范围仍待细化。

## 8. 已确认：草稿与发送待确认记录按会话本地持久保存

用户确认沿用已有 localStorage 的本地保存方式，按会话 ID 保存草稿，以及未确认发送的原始输入和本地提交记录。后端断开、Workspace 卸载、前端刷新或重新打开应用后仍能恢复文字和待确认提示；恢复后先通过 GET 查询事实，不自动重发。

已知 run_id 可以作为恢复线索保存，本地保存的状态不作为服务端权威事实。临时 delta、活动请求、重试计时器和可提交审批身份不从存储恢复为有效状态。startup_id 和动态 base_url 属于请求租约，不能用于将同一会话的持久草稿隔离成不同启动版本。

未采用仅内存保存方案。本地保存失败时的回退、过时恢复线索与当前事实不一致的处理在完整契约中继续细化。

## 9. 已确认：观察与重试随当前会话和窗口生命周期暂停

用户确认只观察当前选中、窗口可见且后端 ready 的会话。切换会话、隐藏到托盘或后端未就绪时，关闭旧观察连接并停止其 GET 请求和重试计时器；保留草稿、发送待确认记录及已经读到的完整事实，不调用取消接口。

重新选中会话、窗口重新显示或后端恢复 ready 后，立即通过 GET 历史重新定位当前 Run，并按已确认查询契约恢复观察或读取终态。生命周期触发恢复与手动重连都应合并为同一恢复任务，不并发建立多条当前观察。前后台变化不重发 POST。

窗口可见性与焦点不同，仅失去焦点不停止观察。已确认的列表轮询在隐藏或后端未就绪时同样暂停；当前宿主已有隐藏/显示操作，前端尚未接入相应窗口可见性输入，需要在实施时补齐。[桌面宿主](../../../../frontend/src-tauri/src/desktop.rs)。

连续失败已达 3 次后，周期性列表轮询不能不断重新开启同一轮重试；手动重连或明确的重新激活动作可以开启新的恢复轮次。

## 10. 已确认：按接口用途分类错误与恢复动作

用户确认分类策略：保留结构化 HTTP status、detail、Retry-After，以及 SSE error 的 code / message / recoverable；列表、消息读取、观察和提交错误分别归属其操作，不使用一个错误字符串覆盖所有操作状态。

| 情况 | 动作 |
| --- | --- |
| 网络故障、GET 503、recoverable=true 的 SSE error | 按已确认 1 / 2 / 5 秒节奏重试 GET，最多 3 次；503 不早于 Retry-After。状态和完整事实保留 |
| POST 503 或连接中断 | 不重试 POST；通过 GET 确认当前事实。没有此次 run_id 时沿用“发送结果待确认”流程 |
| 404 | 停止自动重试，按操作区分会话不存在与 Run 不存在。保留草稿和已有完整事实；Run 404 不能直接当成会话不存在 |
| 发送或审批 409 | GET 读取当前会话/Run 的事实；不自动重发 POST。未提交输入和仍适用的审批选择保留 |
| 列表游标 422 | 保留已加载列表，提示显式重新加载列表；重载时重新建立第一页和分页位置 |
| 发送输入或审批 422 | 保留输入/选择，展示该操作的参数问题；不启动自动恢复循环，也不重试 POST |
| GET 500、recoverable=false 的 SSE error、客户端协议解析失败 | 保留数据和最后确认状态，停止自动重试，提供手动查询/重连及可读错误；不将 Run 改为 error |
| POST 500 | 接受结果可能未知，不直接断言未接受；保留提交记录并 GET 查询，不自动重发 POST |
| GET stream 400，例如错误附带游标 | 请求与协议不兼容，停止自动重试并显示可读错误；不静默更改运行状态 |
| lifecycle error 或当前快照/metadata 的 error 状态 | 展示后端已提交的运行失败及错误事实；这不同于观察失败 |
| 主动切换、隐藏、后端租约撤销导致的 Abort | 属于观察失效/暂停，不显示为网络错误，不消耗重试次数，不取消 Run |

普通第一页轮询继续沿用每 5 秒一次、失败保留列表的契约，不为它叠加另一套自动重试；遇到 Retry-After 时延后下一次请求。审批/取消的具体 pending 与选择保留界面由后续审批票据细化。

## 11. 已确认：审批投影恢复当前仍有效的请求

用户确认 GET Run stream 全量回放时按 seq 处理 required / resolved / invalidated。待审批请求及选择按 thread_id、run_id、checkpoint 坐标和 Interrupt 身份隔离；resolved / invalidated 使对应请求失效，新 checkpoint 的请求不能复用旧请求的可提交选择。

仅在当前 metadata 状态为 interrupted、观察正常完成全量回放，并恢复到仍有效的当前 required 时，提供可操作审批。回放中已有卡片可保留只读，但不能按刚遇到的历史 required 立即开放提交。running 或终态的历史审批不开放提交。

interrupted 回放缺失有效 required 或观察失败时，显示审批尚未恢复并按观察恢复规则处理，不自行猜测审批参数，不将 Run 判为 error。重新恢复后，只有身份完全相同的当前审批可以保留此前选择。

审批按钮、动作参数、拒绝原因、提交 pending、取消交互和选择持久保存范围由[确定审批与取消的完整交互](003-approval-cancel.md)继续决定。本条已确认运行投影中当前审批的有效性。
