# 运行详情、用量与事件契约

日期：2026-10-03。所属票据：[确定运行详情、用量与事件视图](005-run-details.md)。状态：用户已完整确认，规划已定稿；应用和新增查询接口待实施。

本文件统一记录该票据已确认的实施前契约。最终确认见[决议](005-run-details.resolution.md)，真实交流见[讨论记录](005-run-details.discussion.md)；定稿不表示应用已实现或通过测试。前置规则沿用已确认的[查询契约](001-run-discovery.contract.md)、[投影与恢复契约](002-run-projection.contract.md)、[审批与取消契约](003-approval-cancel.contract.md)和[消息与本地资源契约](004-message-tools-export.contract.md)。

## 1. 做什么、为什么、用什么 API

**做什么：**补齐当前会话运行详情、会话栏用量摘要、累计用量和模型分项、真实事件时间线、错误说明与已有恢复入口。

**为什么：**当前抽屉只有 Run ID、原始状态和输入／输出 Token，会话栏用量是固定占位，生命周期和审批事件没有完整保留。详情应解释已经取得的运行事实，让用户区分运行结果、观察连接和用量结算。

**用什么 API：**

| 来源 | 用途 | 当前情况 |
| --- | --- | --- |
| GET /api/threads/{thread_id}/messages | 定位当前会话最近一次运行 | 已有；外层 run_status 是前置契约待补目标 |
| GET /api/threads/{thread_id}/runs/{run_id} | 身份、状态、错误、时间、累计用量、usage_pending | 前置契约已确认，HTTP 查询尚未实施 |
| GET /api/threads/{thread_id}/runs/{run_id}/events | 已提交事件历史 | 前置契约已确认，HTTP 查询尚未实施 |
| 已有 Run SSE metadata／event | 实时更新运行事实和事件 | 已有；前端完整投影待补 |
| 有效取消 POST 返回的 RunSnapshot | 立即确认实际运行终态及当时用量 | 已有；前端按审批与取消契约接入 |
| GET 同一 Run /stream | 用户主动重新连接或核实等待审批 | 已有；沿用前置恢复规则 |

本票据不新增后端字段、端点、事件分页或 Run 列表。GET 查询只读取已提交事实，不启动执行、审批、取消或 Graph 恢复校验；状态权威规则不改变。

## 2. 详情目标与读取时机

### 读取时机

- 进入会话、按历史消息定位最近一次 Run 后，自动读取一次 Run 快照；无需先打开详情，便可让会话栏摘要读取真实用量。
- 打开运行详情时刷新快照，并读取完整事件历史。进入会话时不为了详情主动读取全部事件。
- 已有 SSE 继续更新同一个运行事实投影。打开或关闭详情不另外建立 SSE，不关闭当前观察，也不取消 Run。

### 详情目标与请求安排

- 首版详情跟随当前会话当前／最近一次 Run；不增加历史 Run 列表或切换器。会话内历史消息仍保留所属 Run ID，不把其状态和用量混入当前摘要。
- 会话工具栏和命令面板的“运行详情”、会话栏用量的“查看详情”共用入口。没有 Run 时入口禁用并显示“尚未开始运行”；正在读取身份或读取失败不显示为未开始。
- 快照请求不阻塞 running／interrupted 的既有 GET stream 建立，也不等待快照成功才允许显示已确认的聊天事实。
- 打开详情时，快照与事件可以独立并行请求。两个响应不承诺同一查询时刻，各分区独立显示读取情况。
- 对同一目标的快照请求、事件请求分别不重叠。进入会话后快照仍在读取时打开详情，复用该请求；刷新与自动补读也共用协调入口。
- 已有数据先显示，并标记正在刷新；不得用空白闪烁或加载状态清掉已知字段。快照或事件其中一项失败，不撤掉另一项成功内容。
- “刷新详情”读取快照与事件；自动结算核实只读取快照，不轮询完整事件。
- 会话切换关闭详情。有效新 Run 身份被接受时，仍打开的详情转为新 Run，清空旧 Run 的详情选择与展开状态；旧事实仍保存在所属 Run，不能继承为新 Run 的值。
- 同一会话接受新 Run 身份后，为新目标读取一次快照；若详情仍打开，也读取新目标事件。旧目标请求取消或失效，不能把它们接到新运行。

## 3. 事实合并与请求失效

- 身份使用 thread_id／run_id；RunSnapshot.id 在边界转换为同一运行身份。校验响应属于请求目标后才接入。
- 后端租约、会话选择和目标身份沿用前置契约。旧地址、旧目标或失效请求的迟到响应不更新当前详情。
- 普通 GET 不覆盖有效 SSE 的当前状态；历史 lifecycle 不改写当前状态；已确认终态不回退为 running／interrupted。有效取消写响应仍按前置契约立即确认真实结果。
- 快照其他字段按字段与执行阶段的确认版本合并。请求期间已经取得新的同组用量、结算或执行阶段事实时，旧响应该组字段不得覆盖新事实。
- 错误与结束时间也要检查请求期间的状态变化。较早请求中的 error=null、completed_at=null 不能清掉后来确认的失败或终态时间。
- SSE metadata 只更新实际携带字段。usage=null 是未知，省略 usage 不清空已有值；省略 usage_pending 不等于 false。
- 审批后继续运行属于同一个 Run 的新执行阶段。保留此前累计值供阅读，同时撤销“本阶段结算已确认”的显示；直到取得适用于新阶段的结算事实，不沿用前次 false。
- 建立新观察时，若无法确认仍是之前的执行阶段，旧结算结论先显示待确认。请求被新阶段或同组字段更新淘汰后，按需合并一次新快照读取，不复用过期结论，也不反复排队。
- 当前存储允许取消后的用量补交，而不必再次更新 Run.updated_at；因此不得仅靠 updated_at 相等就丢弃新用量，也不得仅靠更新时间对所有字段判新旧。
- JSON events 与 SSE event 按 thread_id／run_id／seq 合并、按 seq 升序呈现。一轮查询没有返回某条已知事实，不表示应删除它。
- 已提交事件不按文字、时间或工具名称去重。同身份同 seq 的冲突按协议问题处理，保留已确认内容；消息兼容缺省 generation_status=complete 的规则沿用消息契约。

## 4. 用量显示

### 明确区分值和结算状态

| 情况 | 用量区域 |
| --- | --- |
| 确认尚无 Run | “尚未开始运行”，不展示零数值 |
| 有 Run，首次读取未完成，且无已知用量 | “正在读取用量” |
| usage=null，或尚无可用用量事实 | “暂无用量数据”，不填 0 |
| 有有效 Usage | 显示已累计输入、输出、总量和已记录模型调用次数 |
| usage_pending=true | 显示“仍在结算”；已有值继续显示为已累计 |
| 适用于当前阶段的 usage_pending=false | 有用量时显示“当前用量已保存”；没有用量时仍显示暂无数据，不能补造零 |
| usage_pending 省略或本阶段尚未重新确认 | 显示“结算状态待确认”，不沿用旧阶段已保存的结论 |
| 本轮自动核实达到上限且仍为 true | 显示“仍在结算，自动核实已暂停”，提供“继续核实” |
| 读取失败 | 保留已有值，局部提示“用量读取失败”及重试，不改成 Run 失败 |

- 用量是本次 Run 已记录的累计值，包含审批后继续前的已记录部分。它不是会话全部运行的合计，也不是上下文占用、实时速度或费用。
- 数值直接展示响应里的 total_input、total_output、total_tokens、calls；不因模型分项不齐而重算、补零或修改总量。后端实际提供的 0 可以正常显示，但不宣称供应商实际未消耗。
- calls 显示为“模型调用次数（已记录）”。当前 TokenTracker 记录模型完成回调，不能解释成全部尝试次数、工具调用次数或准确计费次数。
- 模型分项使用 by_model 的实际键及 input／output／calls。模型名称缺失时不能用占位模型补一行；by_model 为空显示“暂无模型分项”。
- 模型分项默认折叠，展开后显示全部已提供模型。长名称换行或在区块内阅读；不存在的模型总量字段不自行添加。
- Run 已完成／已取消／运行失败时，用量仍可为待结算。用量已保存时，Run 仍可为等待审批；两种状态各自显示。

### 会话栏摘要

- 现有会话历史栏底部改为“本次运行用量”，消费同一 Run 的事实。
- 保持紧凑结构：输入与输出一行、合计与已记录调用次数一行，结算提示和“查看详情”位于其下；未知与读取失败用对应文字替代数值。
- 数字按本地格式分组，保留真实值，不用百分比、进度条或虚构上下文上限。长数字允许换行。
- 切换会话或接受新 Run 后，不短暂展示前一个 Run 的用量。窄屏侧栏隐藏不阻断既有详情入口，也不改变读取与观察身份。

## 5. 结算后的后续核实

### 何时补读

- 同一观察代次正常结束于 interrupted 或终态时，补读一次只读 Run 快照，确认用量结算、错误和时间。重复 EOF 不重复安排。
- 接受有效取消终态快照时立即显示实际结果；若当时仍待结算，随后核实。取消回应与正在进行的快照补读合并，不发起并发重复查询。
- 手动刷新、进入会话或重新显示窗口时也可更新快照。所有触发信号共用请求协调；列表每五秒刷新不能额外开启一组结算计时器。

### 有上限的自动核实

- 当前窗口可见、后端就绪、目标仍是当前会话 Run，且其已确认状态为 interrupted／completed／cancelled／error、usage_pending=true 时，启动结算核实。
- 每次快照请求结束后等待 5 秒，再请求一次；本轮最多 12 次后续快照请求，失败请求和重试也计入该上限。已有首次补读不算这 12 次。
- 运行中有正常 SSE 时不因 pending=true 再叠加定时快照轮询；使用 SSE 与阶段结束补读。观察故障仍按前置 GET 恢复处理，不由用量轮询替代。
- 查询得到适用于当前阶段的 usage_pending=false 时立即停止。不能根据“过了一分钟”、用量数字没变化、SSE 结束或终态自行改成 false。
- 可恢复读取错误遵守既定 1／2／5 秒、最多三次自动重试及 Retry-After；不另开轮询与重试两套任务。成功但仍待结算也不重置本轮 12 次预算。
- 三次自动重试仍失败时停止本轮自动核实，不以五秒轮询绕过失败上限；保留数据并提供手动重试。
- 404、GET 500、不可恢复错误或协议错误停止自动核实，保留数据与错误。普通查询失败不会重启后端、重建 Graph 或重新发起 POST。
- 达到上限时保留最后事实并提示自动核实已暂停，不显示运行失败。“继续核实”由用户主动发起一次读取，若仍待结算，可开始新的受限轮次，并遵守尚未到期的 Retry-After。
- 关闭详情不停止当前会话摘要所需的结算核实；切换会话、隐藏窗口、租约失效则停止计时器并取消相关 GET，不取消 Run。
- 同一后端租约内，关闭／重开详情或切走／切回，不重置同一执行阶段已经消耗的自动核实预算。重新进入仍可读取一次快照，但不能以此无限重新开启轮询。
- 新执行阶段、有效新后端租约或用户明确“继续核实”可开始新轮次；审批继续后的旧轮次先失效，不能用旧响应确认新阶段。
- 主动 Abort 不显示网络故障，也不计为失败重试。已有累计值与最后事实保留；恢复显示后依前置恢复流程重新确认目标。

若后端进程停止前没有结算记录，纯读 GET 可能一直返回 pending=true；首版只说明未确认和提供手动核实，不承诺自动补交、跨进程续跑或供应商账单查询。

## 6. 身份、状态、时间和错误

- 顶部沿用当前会话标题和中文 Run 状态。会话 ID、运行 ID 分别提供完整复制；长 ID 使用等宽字体、可选择和换行，复制不取省略后的文本。
- 状态文案沿用“运行中／等待审批／已完成／已取消／运行失败”；无 Run 的“未开始”仅用于确认没有运行的情形。
- 创建时间、最近更新时间、结束时间来自已取得的快照；按系统本地时区显示完整日期时间并标明时区，提供原始 UTC 值的查看／复制。
- running／interrupted 的 completed_at=null 显示“尚未结束”；终态尚无有效结束时间显示“结束时间未取得”。不以本地收到事件的时间替代服务端时间。
- 不推导单条消息、工具或模型的准确耗时，不增加虚构速度、费用、完成百分比。
- 当前 Run 失败时，展示已确认的 error 与 error_code，支持完整查看和复制。尚未读到错误详情时提示“后端错误详情尚未取得”，不把观察或详情 GET 错误填成执行错误。
- 当前有效 lifecycle error 的正文可先显示；之后由有效快照补齐。历史事件中的错误保留在事件行，不覆盖另一个 Run 的当前错误。
- 运行结果、观察连接情况、详情读取情况分区表达，错误不能只靠颜色或 toast。

## 7. 已提交事件时间线

### 顺序与范围

- 事件来自现有 SSE 与只读 events 查询，默认显示生命周期与审批事件。提供“包含消息事件”开关查看已提交 message 事件；此开关只过滤呈现，不丢弃完整记录。
- 每行显示中文类别、真实事件文字、服务端 created_at 和 seq。按 seq 升序，不按客户端接收顺序或时间字符串排序。
- 序号允许空洞；缺号不自动提示丢失。已加载条数说明当前客户端记录范围，不伪称服务端未来不会再产生事件。
- 相同事件重放只保留一行；新增事件不抢用户正在阅读的滚动位置。
- 读取中、查询失败、已加载但过滤后为空分别提示。真正尚无已提交事件显示“暂无已提交事件”；仅隐藏消息造成空视图时显示“暂无运行或审批事件”。

### 事件文字与只读详情

| 公开事件 | 显示方式 |
| --- | --- |
| lifecycle status_changed | 按 payload.status 显示“进入运行中”“等待审批”“运行已完成”“运行已取消”或“运行失败”；有真实 message／error_code 时保留 |
| approval required | “请求审批”，显示可识别的真实请求摘要；完整 checkpoint、Interrupt 和动作内容可查看 |
| approval resolved | “审批已处理”，仅按实际 responses 显示批准／拒绝与真实拒绝原因 |
| approval invalidated | “审批已失效”，原因按实际 reason 显示；当前 run_cancelled 表示因运行取消失效 |
| message created | “用户消息已保存”“Agent 消息已保存”或“工具结果已保存”；消息中止标记、工具状态按各自真实字段另列 |

- 不从本地审批草稿、提交按钮、HTTP 200、取消点击或当前终态编造 resolved／invalidated。没有取得对应事实时说明尚未读取对应事件。
- 未知或不能识别的详情保留完整原始载荷，不猜测动作、原因或工具结果。协议不兼容在所属读取区域提示，不伪造运行失败。
- 无法通过协议校验的记录只作为读取问题的只读原文，不接入已确认事件、消息或当前审批投影。
- 事件行默认折叠，展开提供完整格式化 JSON。支持“复制完整事件”，包含实际 seq、created_at、category、event_type、payload 等已提供字段，不取摘要或可见截断内容。
- 长 JSON 延续最高约 320px 区块内滚动及完整查看。完整查看使用同一前景抽屉／底部面板的只读子视图，返回时保留时间线位置和焦点，不叠加多个模态。
- 事件详情不放另一套审批控件，也不把历史 required 当成当前可操作请求。处理审批仍回到聊天卡片。
- 本地路径、网页或图片在事件 JSON 中保持原文，不能自动打开或预览；本地资源只按消息契约的 Agent Markdown 入口处理。

### 补读与终态竞争

- 打开详情后读取事件；此后 SSE 的已提交事件继续合并，不为每条新事件再 GET 全量历史。
- 详情仍打开时，正常 interrupted／终态观察结束或接受有效取消终态，补读一次事件，填补真实审批失效、生命周期和已保存消息记录。
- 若当前 events 请求开始于终态确认之前，结束后可以合并一次在确认之后发起的补读；重复终态通知不并发、也不不断排队。
- 关闭详情取消仅为该详情发起的事件读取与重试，并停止其后续补读；保留已经接入的完整事件，当前 SSE 仍继续。
- 终态已确认但事件尚未读到时显示“正在读取运行记录”或局部读取失败；不凭当前状态造一条终态事件。
- events 与快照分别成功并不证明它们来自同一时刻。终态消息补读仍沿消息契约独立完成；事件读取或用量结算不能替代中止正文保存确认。

## 8. 读取错误与恢复入口

- 快照、用量结算、事件查询的读取错误各自归属相应分区；保留已显示事实，不影响草稿、审批选择或已经保存的消息。
- 网络／503 等可恢复 GET 错误沿用三次自动重试和 Retry-After；同一请求不再附带另一套立即重试。503 期间手动按钮说明等待，并防止重复请求。
- 404 停止自动重试，提示“运行不可读取”，提供“重新读取会话”以重新定位；不直接删除整个会话或新建 Run。
- GET 500／协议解析失败停止自动重试，提供手动“重试读取”。不把读取失败、宿主 stderr 或 stream_failed 当作后端 Run.error。
- “刷新详情”只刷新当前目标快照与事件。请求 pending 时禁用重复动作，已有可阅读内容和关闭入口保留。
- 观察异常时提供既有“重新连接”入口，调用同一 Run GET stream 并复用前置恢复协调；它不是重新执行，不会自动重发发送或审批 POST。
- 当前审批尚未核实时可提供“核实审批”调用既有 GET stream；只有经过完整暂停回放核实的请求才开放审批操作，JSON events 不代替该校验。
- “处理审批”关闭详情并定位当前聊天卡片；审批提交与取消仍使用已确认的统一入口和确认弹窗。本详情不增加第二套审批选择或直接取消动作。
- 终态提供“返回会话”，关闭详情并把焦点返回可用聊天入口；不提供语义不明的“重试运行”按钮。
- 关闭详情、Esc、布局变化、读取失败或点击恢复均不隐式取消 Run。

## 9. 样式与可访问性

- 延续[当前设计规范](../../../../frontend/design.md)：桌面 400px 覆盖抽屉，窄屏底部面板；白色背景、Slate 分隔、Indigo 操作、Geist／JetBrains Mono、Phosphor regular。
- 详情按“运行信息／本次运行用量／事件记录”垂直排列。身份和数值使用普通键值行，模型分项折叠，事件使用细分隔和紧凑记录行；不另加仪表盘或嵌套大卡片。
- 状态有可读中文和对应图标，已取消用中性样式，运行失败使用已有危险语义色；待结算不用运行失败红色。
- 抽屉标题和关闭入口保持可达，内容整体可滚动；只有长 JSON、代码或必要表格在自己的区块内滚动，不撑宽整页。
- 重要文字不小于 14px，窄屏操作目标不小于 44px。复制、过滤、展开、刷新与恢复可用键盘，焦点样式清晰。
- 同时仅一个前景模态。关闭或返回子视图时恢复到仍存在的入口；目标已改变时返回当前工作区，不能聚焦旧会话节点。
- 读取与错误使用适量 aria-live；Token 数字、事件回放和每条 delta 不逐项反复播报。更新事件不抢滚动或焦点。
- 原稿与桌面截图的视觉基准已确认，原生 Tauri 完整详情与四档视口在实施后验收，不能用文档定稿推断实机通过。

## 10. 模块位置与实施衔接

**后端：**纯读查询位于 Runtime／持久查询边界，经 HTTP 适配返回已确认 RunSnapshot 和公开事件；共享现有 SSE 事件投影。用量沿用现有结算记录，不为详情查询调用会写入恢复错误的旧 read_run 流程。

**前端运行事实：**身份、状态、用量、错误、时间和事件由同一按会话／Run 隔离的投影保有。会话栏、聊天和详情读取它，不能各自维护一份互相竞争的 Run 状态。

**前端详情查询：**负责按需快照／事件读取、独立分区读取状态、同目标请求协调、执行阶段确认、结算预算、租约／选择失效与局部重试；不拥有 Agent 执行，不发起隐式 POST。

**只读详情呈现：**负责键值行、模型分项、事件过滤、完整内容和复制、恢复入口与焦点，依赖现有 Overlay。审批与取消仍由既有统一交互处理。

后续[确定首版交互补全与验收顺序](006-interaction-acceptance.md)需纳入以下可判定场景：

- 进入会话自动读快照、事件按打开详情读取；有缓存刷新不闪空，两个分区分别失败不互相清空。
- 旧查询晚于新 SSE／审批继续返回，不覆盖新阶段的状态、用量、结算、错误或结束时间。
- usage=null 不显示 0，真实 0 如实显示；by_model 缺项不补模型、不重算总量，calls 不显示成工具次数。
- 取消终态先到、用量后到，已保存正文、终态、事件和结算分别确认；GET 故障不变成 Run.error。
- pending=true 后续核实停止于 false 或请求上限；Retry-After、三次恢复上限、隐藏／切换／新租约和重复通知不产生并发或无限轮询。
- 重放／重复事件只有一行，seq 空洞不报丢失；本地选择不出现在审批历史，终态未读到的事件不伪造。
- 抽屉关闭不停止观察或取消运行；长 ID／模型／JSON 可完整复制，窄屏与只读子视图可返回并保持焦点。

上述场景是后续实施与验收输入，本轮没有新增或运行应用测试、构建、真实模型任务或原生文件打开。用户主导实现；本票据已完成规划决策，应用实施与验收仍待完成。
