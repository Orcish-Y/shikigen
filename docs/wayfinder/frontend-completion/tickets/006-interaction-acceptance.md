# 确定首版交互补全与验收顺序

## Question

在前置接口和核心交互明确后，如何形成覆盖 PRD 首版全部 17 条标准及用户补充的中止消息保存、本地资源要求的实施顺序与可判定验收，避免只补主路径而遗漏历史、输入、窄屏、错误与可访问性？

**做什么：**确定真实日期分组/标题/相对时间、列表 skeleton 与失败重试、空状态、Enter/IME、运行中草稿、流式滚动、Cmd/Ctrl+B、命令面板可用性、768–1279px 覆盖导航及触控操作；最终拆分可由用户实施的任务。

**为什么：**这些能力多数无需新后端，却仍是完整首版体验的组成部分。现有模板/早期截图不能证明真实审批、取消和恢复在各档视口可用。

**API：**现有 Thread 时间与消息字段、前端状态和原生 dialog；恢复/审批/取消沿用前置票据最终契约。需要保存标题的 PATCH 和独立管理页面不纳入首轮。

**需要决定的边界：**1440×900、1280×800、1024×768、390×844 均覆盖核心操作；失败保留输入和选择；上翻不抢滚动；关闭模态返回焦点；错误/正常 EOF/Run 终态可区分；验证包含重放、切换、迟到、重复、竞争与结算，而非只验证布局或用 mock 宣称真实模型已经通过。

[审批与取消交互契约](003-approval-cancel.contract.md)已定稿：底部定位审批、卡片统一提交、参数默认折叠、审批草稿跨重启保存并核实恢复、请求互斥和一次取消弹窗。模态和焦点行为已有依据，本票据统筹其在长内容、键盘、窄屏和四档视口中的验收，不重新决定这些已确认规则；应用实现仍待完成。

用户已确认以两份 HTML 原稿和项目桌面展开／收起截图定稿视觉基准，其他实机核对放到实施后，见[视觉基准决议](007-native-style-baseline.resolution.md)。视觉目标见 [design.md](../../../../frontend/design.md)，实际证据与未观测范围见[视觉复核记录](007-native-style-baseline.evidence.md)。本票据应统筹原稿比例、导航头层级、消息排版、输入密度及 HTML／Tauri 内容区尺寸换算；不能把 PNG 图片像素当作 CSS 断点。视觉依赖已关闭，本票据于 2026-10-04 由 codex 认领，交互和实施／验收顺序仍待解决。
