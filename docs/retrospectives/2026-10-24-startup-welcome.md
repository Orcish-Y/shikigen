# 启动欢迎页修复：耗时与 token 成本复盘

日期：2026-10-24。关联任务：[启动新会话修复与验收记录](../../.scratch/startup-new-conversation/PRD.md)。

## 结论与统计边界

主要责任在主 agent 对修复范围、验证流程和成本的控制。环境加载慢放大了浪费，不能用它解释重复执行、错误判断和无效排查。使用轻量测试子 agent、充分验证核心会话逻辑本身符合现有约定，问题出在编排方式。

首批回归测试文件于 15:40 创建，验证报告于 16:32 创建，仅这一段就约 51 分钟，不含更早排查。文件时间只说明这段跨度，不等于准确的总工作时长。没有完整计费遥测，无法给出总 token、金额及各阶段占比。

## 具体失误

| 失误 | 本次证据与代价 |
| --- | --- |
| 开始时没有对齐验收终点 | 最初考虑失效会话回退，用户再次指出启动应显示新会话欢迎页。随后实现涉及新草稿、首次发送创建会话及竞态保护；这些行为符合最终需求，但没有先比较最小修复范围，导致测试迁移面扩大。 |
| 重复启动慢检查 | 类型检查约 130 秒，构建约 210 秒，组件导入也有数十秒冷加载。多次中断、单项重跑及整批重启反复支付相同成本，没有先建立正常耗时基线。 |
| 验收环境检查太晚 | 只确认桌面 helper 存在，误以为本次未改 Rust 就无需重建。实际二进制旧于相关源码，不支持本次验收 origin，白跑两项原生验收。另有 loopback 权限失败，应先做小型环境检查。 |
| 首次失败证据不足 | 测试报告器只记用例名称和结果，未保存 OpenAPI 首次失败的断言、堆栈和 DOM。复跑通过仍无法定位原因，增加执行成本，也留下归属不明的问题。不能据此声称是环境偶发。 |
| 通过条件后置 | 最初截图仍处于加载或校验状态，后来才补上“发送按钮可用”的等待，又重跑原生验收。稳定状态应在第一次验收设计时确定。 |
| 主 agent 微观管理过多 | 多次查询状态、读取大段输出、重复推演与调整测试安排；测试被中断后又需重新交接。高成本上下文花在验证编排上，未充分发挥轻量测试 agent 的独立执行能力。 |

这些失误使工具调用、重复上下文和主 agent 推理一起膨胀。不能把 token 成本简单归因于“测试多”，也不应通过减少必要验证来解决。

## 下次同类修复的执行检查点

以下是本次复盘提出的执行改进，不修改 AGENTS.md 或新增全库协作约定。

1. **先固定验收终点。** 本例应先明确：完整启动显示欢迎页、不请求失效历史、首发只创建一次且原文正确、历史草稿保留、托盘恢复保持会话。再选择实现范围。
2. **先检查验证入口。** 确认端口和权限、二进制与源码是否匹配、测试加载基线；日志从第一次运行就保留断言和堆栈。截图等待条件包含页面稳定及可交互。
3. **开发定向检查，最终集中验证。** 主 agent 做必要的快速检查；按现有约定，一次完整交接给轻量测试 agent 执行最终相关回归、类型检查、构建和原生验收。没有新改动、新失败或覆盖缺口时，不重复已通过的批次。
4. **超时先改善观测。** 区分加载、执行和输出缓冲，结合基线决定等待时间。同一命令重复失败或超时后先获取新证据，不继续盲目重启；避免不断中断测试 agent。
5. **给附带失败设边界。** 保存第一次失败证据，做有依据的定向复现；归属未明时准确记录，不通过反复追求全绿扩大任务。未完成的整批运行不能报成整批通过。
6. **控制主 agent 消耗。** 文件与日志按问题定向读取，避免大段截断后重读；进度更新说明新发现或正在等待的具体检查，不重复猜测。发现执行成本持续增加时及时调整方法，保留必要验证，不新增无谓审批。

下次开工先检查第 1、2 项，最终交接时检查第 3 项，异常时执行第 4、5 项。若以后需要将这些内容固化为 AGENTS.md 或技能约定，再单独征得用户确认。
